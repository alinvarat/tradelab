# คู่มือปฏิบัติงาน TradeLab (Runbook)

ไฟล์นี้บอกว่าแต่ละวันต้องทำอะไร ทำอย่างไร และเมื่อไหร่จึงนับว่าเสร็จ
- เป้าและแผนดูที่ `ROADMAP.md` (ข้อ 1.5)
- สถานะล่าสุดดูที่ `reports/STATUS.md`
- สเปกของแต่ละเส้นกลยุทธ์อยู่ใน `ops/lines/`
- กฎความปลอดภัยและกฎวิจัยอยู่ใน `AGENTS.md` ข้อ 1–9 กฎเหล่านั้นใช้ทุกขั้นในไฟล์นี้

---

## 1. เริ่มงานทุกรอบ (ทำตามลำดับ)
1. ดึงโค้ดล่าสุด
   ```bash
   cd /home/alinvarat/Project/tradelab && git switch main && git pull --rebase origin main
   ```
2. อ่าน `reports/STATUS.md` ทั้งไฟล์ แล้วเลือกงานแถวบนสุดที่สถานะไม่ใช่ `done` หรือ `killed`
3. ตรวจว่าไม่มีคนอื่นทำงานเดียวกันอยู่
   ```bash
   gh pr list --state open && gh run list -L 10
   ```
4. ตรวจสุขภาพระบบตามข้อ 2 ทุกครั้งที่เริ่มงาน และทำก่อนงานอื่น
5. เปิด branch ใหม่ให้ชื่อตรงกับงาน: `line/L1-screen`, `app/<เรื่อง>`, `ops/<เรื่อง>`

## 2. ตรวจสุขภาพระบบ (5 นาที)
| ตรวจอะไร | วิธี | ปกติ | ถ้าไม่ปกติ |

บันทึกผลตรวจลงแถว "สุขภาพระบบ" ใน `reports/STATUS.md` พร้อมเวลา UTC

## 3. นิยาม "เสร็จ" (Definition of Done)
งานแต่ละประเภทจะถือว่าเสร็จเมื่อครบทุกข้อในแถวของตัวเอง:

| ประเภทงาน | ต้องครบ |
|---|---|
| แก้แอปหรือบอท | 1) มีเทสต์ใหม่ที่ล้มก่อนแก้และผ่านหลังแก้ 2) CI บน PR ผ่าน 3) merge แล้ว deploy บน main ผ่าน 4) เปิดหน้าเว็บผ่าน Chrome แล้วเห็นค่าที่เปลี่ยน 5) อัปเดต `reports/STATUS.md` |
| ด่านคัดกรอง (screen) | 1) ผลลง `research/studies/RESULTS.md` พร้อมตัวเลขทุกข้อที่สเปกกำหนด 2) ไฟล์ผล JSON อยู่ใน artifact ของ Actions 3) ตัดสินผ่านหรือตัดตามเกณฑ์ที่เขียนไว้ก่อนรัน 4) อัปเดตสถานะเส้นใน `reports/STATUS.md` |
| ล็อก protocol | 1) ไฟล์ `research/studies/protocol_<line>.md` มีวันที่ล็อก, กติกาเข้าและออก, ต้นทุน, control และเกณฑ์ e-process 2) merge เข้า main **ก่อน** ข้อมูลชุดทดสอบชุดแรกเข้ามา |
| เอกสาร | ไม่ขัดกับโค้ด และลิงก์ทุกลิงก์ชี้ไปไฟล์ที่มีอยู่จริง |

ถ้ายังไม่ครบ ให้รายงานตามจริง เช่น "รวมแล้วแต่ยังไม่ขึ้นระบบ เพราะ deploy ล้ม" ห้ามรายงานว่าเสร็จ

## 4. ขั้นตอนเพิ่มด่านคัดกรองใหม่ (ใช้กับทุกเส้นใน `ops/lines/`)
1. อ่านสเปกของเส้นนั้นใน `ops/lines/Lx_*.md`
2. เขียนเกณฑ์ผ่านและเกณฑ์ตัดลง `RESULTS.md` ในหัวข้อใหม่ "Lx screen (pre-registered <วันที่>)" **ก่อน** เขียนโค้ดดึงข้อมูล
3. เขียนฟังก์ชันคำนวณแบบ pure ใน `core/screens.py` ฟังก์ชันรับ list ของ dict และคืน dict ผลลัพธ์ ห้ามเรียกเน็ตภายในฟังก์ชันนี้
4. เขียนเทสต์ offline ใน `tests/test_screens.py` ใช้ข้อมูลปลอมขนาดเล็กที่รู้คำตอบล่วงหน้า
5. เขียนฟังก์ชันดึงข้อมูลและฟังก์ชัน `study_<line>` ใน `research/studies/run.py` แล้วเพิ่มชื่อลงใน `STUDIES`
6. เพิ่มชื่อ study ลงใน `matrix.study` ของ `.github/workflows/research.yml` บรรทัด `study: [...]`
7. push ไปที่ branch `research-run/<line>` ซึ่งสั่งให้ Actions รันอัตโนมัติ หรือสั่งรันเอง
   ```bash
   gh workflow run "Research studies" -f study=<line> --ref <branch>
   ```
8. ดาวน์โหลดผลแล้วอ่านตัวเลขจริง
   ```bash
   gh run download <run-id> -n study-<line> -D /tmp/claude-1000/<line>
   ```
9. เขียนผลลง `RESULTS.md` ตัดสินตามเกณฑ์จากขั้นที่ 2 แล้วเปิด PR รวมผล

**ข้อจำกัดของเครื่อง Actions (สหรัฐ):**
- `api.binance.com` และ `fapi.binance.com` ถูกบล็อก ให้ใช้ `https://data-api.binance.vision/api/v3/klines` สำหรับราคา spot
- funding ของ perp: ลอง OKX (`https://www.okx.com/api/v5/public/funding-rate-history`) ก่อน เพราะ Bybit มักบล็อกเครื่องในสหรัฐ
- ถ้า endpoint ถูกบล็อก ให้ย้ายงานดึงข้อมูลไปรันบน Kuber ผ่าน `core/market_collect.py`

## 6. เมื่อมีปัญหา (Incident playbooks)
### 6.1 deploy ล้ม
1. อ่านข้อความ error
   ```bash
   gh run view <id> --log-failed | grep -E "KuberApi|error|✖" | tail -5
   ```
2. **ถ้าข้อความเป็น `KuberApiError`, `Service Unavailable` หรือ `Unable to resolve pushed image digest`** แปลว่าปัญหาอยู่ฝั่งแพลตฟอร์ม ห้ามแก้โค้ด ให้รันซ้ำทุก 10 นาที สูงสุด 6 ครั้ง
   ```bash
   gh run rerun <id> --failed
   ```
   ถ้ายังล้มหลังครบ 1 ชั่วโมง ให้แจ้งเจ้าของว่าต้องให้ผู้ดูแล Kuber ตรวจ และบันทึกลง STATUS
3. **ถ้าล้มที่ขั้น test** ให้แก้โค้ดตาม skill `systematic-debugging` แล้วเปิด PR ใหม่
4. ระหว่างที่ deploy ยังไม่ผ่าน ให้ระบุใน STATUS ว่าบอทบน Kuber ยังเป็นเวอร์ชันของ PR ไหน

### 6.2 บอทหยุดสแกน หรือมี error
1. อ่านค่า `error`, `paused` และ `last_scan_age_s` จาก `/api/llm_trader`
2. ถ้า `paused` เป็น true ให้หาเหตุผลใน `decisions` ล่าสุด
3. ห้ามสั่งรีสตาร์ตหรือแก้ state บน volume โดยตรง ให้แก้ผ่านโค้ดและ deploy เท่านั้น

### 6.3 ค่า AI สูงผิดปกติ
1. เทียบ `usd_today` กับจำนวนครั้งที่เรียกโมเดล (`calls_today`) ค่าปกติคือราว 0.005–0.01 USD ต่อครั้ง
2. ถ้าเกินช่วงนี้ ให้ตรวจขนาด prompt และอัตรา cache hit จาก OpenRouter (เจ้าของดูได้ที่ Activity)
3. บันทึกสาเหตุและตัวเลขลง `reports/COSTS.md`

### 6.4 ตัวเก็บข้อมูลหยุด หรือพื้นที่ใกล้เต็ม
1. ดูค่า `last_error` และ `files` จาก `/api/collect`
2. ถ้า `paused_low_disk` เป็น true ให้เปิด PR ย้ายไฟล์เก่าไปเก็บที่ data branch ห้ามลบข้อมูลบน volume เอง
