# Protocol Q1-0: wallet-follow counts-only probe, locked 2026-11-27

Plan: `research/plans/PLAN_20261127_fable.md`, direction Q1, kill test (0). Simulated money and public endpoints only; no keys, no account, no orders. Runs on GitHub Actions only (`wallet_follow.yml`, mode `probe`). Code: `wallet_follow_core.py` (pure), `wallet_follow.py` (fetch). **No P&L, return, win rate or rank is computed in this step**; only counts, dates, medians of hold length and entry price, and HTTP behaviour. A rule below changes only by a dated addendum written before the first affected row. The protocol for tests 1 and 2 (persistence, one rule) is a separate file, locked after this probe is read and before any return is computed.

## 1. Point-in-time rules that bind every later step (written now so the probe frame is the same one)
- Wallet frame: built from the **global trade feed** (`/v2/trades?start=&end=`), never from `/v2/leaderboard`, `/v2/biggest-winners`, `/v2/user-pnl`, `/v2/user-stats` or current `/v2/positions` (all are as-of-today and carry survivorship). Hyperliquid: the leaderboard is as-of-today; it is used only to measure history depth and a Hyperliquid arm is runnable only if a point-in-time frame exists.
- Frame windows: one hour at 12:00 UTC on the 1st of each month 2025-01 .. 2026-10 (22 windows), up to 3 pages of 1,000 rows each; a wallet joins the frame with any row of notional (price x size) >= 500 USD. Sampling order: sha256("q1-wallet-probe-20261127" + wallet), first 200. No outcome is read to choose wallets.
- Per sampled wallet: `/v2/trades?user=` paged newest-first up to 25 pages (25,000 rows). A wallet whose history ends at the cap is **counted as truncated and reported**, never silently dropped.

## 2. Counts reported
Per route: HTTP status and key names for status, global trade window, user trades, activity, positions, positions snapshot at 2025-06-01 and 2026-10-01 (does it differ, i.e. is it historical), resolutions, gamma by condition. Rate behaviour: calls, 429s, errors, seconds per call. Frame: wallets per window, new wallets per window, share of wallets added by the last 5 windows (saturation). Wallets: earliest trade, months back, distinct conditions, distinct resolved conditions (gamma `closed` and `closedTime`; checked for the first 150 conditions of a wallet, a lower bound), duplicate rows (key: tx, token, side, price, size, time), share of wallets that bought both tokens in more than half of their conditions (market-maker marker). Positions with buy cost >= 500 USD: count, hold days (first buy to the wallet's own exit if it sold >= 95% of the shares, else the market's close time), median entry price. Hyperliquid: leaderboard rows and keys, `userFillsByTime` from 2025-01-01 for 20 sampled wallets (rows, earliest fill, rows at the 2,000 cap), `portfolio` history length, whether `recentTrades` carries wallet addresses.

## 3. Decisions (fixed now)
- **Kill 0a (wallets):** a wallet qualifies if its earliest trade is on or before 2025-05-26 (18 months before 2026-11-26) and it has >= 100 distinct resolved conditions. Estimated qualifying wallets = frame size x (qualifying / sampled). Pass if >= 300. If < 300 and the frame saturated (the last 5 windows added < 20% of the wallets) the direction is **killed**; if < 300 and it did not saturate the verdict is `extend_frame` (one dated addendum with more windows, then re-read once).
- **Kill 0b (standalone ceiling):** ceiling = (1 / (median entry price + 0.01)) ^ (30 / median hold days) for positions >= 500 USD with a known exit. Under 3.0 the direction is `component_only` (it may still enter the book as a small component); it is not killed by this alone.
- **Hyperliquid arm:** runs only if its probe shows fills reachable back to the first split date for most sampled wallets and a frame that does not come from the leaderboard. Otherwise the written result is "arm not runnable point-in-time".
- A failed endpoint is a probe result, not a reason to work around authentication.
